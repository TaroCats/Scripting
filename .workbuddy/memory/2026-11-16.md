# 2026-11-16

## 亲邻开门工具：门禁列表排序 + 收藏，小组件按该顺序展示

- 新增 `core/door_prefs.ts`（纯函数）：`DoorPrefs = { order, favorites }`，键 `ql_door_prefs`。
  与 `ql_doors` 分开存的原因：`queryUserDoorByCache` 每次同步都会覆盖服务端顺序，用户排序会被冲掉。
- `arrangeDoors()` 是唯一展示顺序来源：收藏组在前 + 组内按手动顺序 + 未知 id 落到未收藏组末尾。
- `normalizePrefs()` 在每次同步后调用（App 的 `persistDoors`、`widget_shared.syncDoors`），剔除消失的 id、追加新门禁。
- App 新增第 2 个 Tab「门禁」：收藏区 / 其他区各一个 `ForEach` + `onMove`，右上 `EditButton` 进拖拽模式。
  分两组是为了避免跨收藏边界的拖动被弹回。
- 收藏 = 置顶 + 小组件优先。小尺寸/锁屏显示 `arrangeDoors()[0]`，中/大尺寸按顺序取前 3/5 项（收藏项带 ★）。
- `Widget.reloadAll()` 在偏好变更后立即刷新时间线。
- 验证：13 项逻辑自测（bun + stub Storage，写入后 Object.freeze 模拟运行时冻结）+ `tsc --noEmit` 14 文件零错误。

### 踩到的坑
- `toggleFavorite` 第一版只从 `prefs.order` 推顺序，而 `order` 只含被操作过的 id，
  导致未记录过的门禁被挤到收藏项后面。修法：签名改成 `toggleFavorite(prefs, fullIds, id)`，
  `fullIds` 必须是全量已排序 id。
- 系统原生 `reorderContainer` 是 iOS 27+，为兼容性仍用经典的 `EditButton` + `ForEach.onMove`。

## 修两个线上 BUG（同一天晚些）

1. **门禁列表拖动/收藏后自动跳回「开门」Tab**
   - 去掉交互路径里的 `Widget.reloadAll()`（只在「刷新小组件」按钮里显式调用）
   - 把门禁页拆成独立组件 `DoorListTab`，prefs 由它自己从 Storage 读写，父组件不重渲染 TabView
   - 当前 Tab 落盘 `ql_tab`，重挂载后原位恢复；`?from=widget` 时强制落在开门页

2. **小组件点击无反应**
   - 根因：根容器挂了 `widgetURL`，整块变成打开 App 的热区，把 Button 的 AppIntent 抢掉
   - 改为各视图内部用 `<Link url={...}>`，开门按钮与 Link 做兄弟节点
   - 补反馈：中/大尺寸显示「最近结果 + 时间」，小尺寸 30 分钟内点过也显示
   - Intent 入口先写「收到开门请求」日志，用于分诊"按钮没点到" vs "请求卡住"

经验：Scripting 小组件里 **根级 widgetURL + 内部 Button intent 不能共存**。交互小组件一律 per-region Link。

## 小组件"少了前两个门禁 / 顺序不对"（同日第三轮）

结论：**不是排序错，是小组件时间线是旧快照**。上一版为了修跳页把 `Widget.reloadAll()` 从交互路径删了，
WidgetKit 只在 30 分钟或显式请求时重跑 widget.tsx。同步时 `commonlyUsedDoor` 会被 unshift 到列表最前，
所以旧快照看起来正好"少了前两项"。

- 修：`AppEvents.scenePhase === "background"` 且 `widgetDirty` 时 `Widget.reloadAll()`；外加「刷新小组件」按钮
- 加固：`arrangeDoors`/`normalizePrefs` 里 id 一律 String() 比较（number 型旧数据会整体错位）
- 新增 `healPrefs()`：启动时若 order 未覆盖全部门禁（早期版本遗留的半截 order），按服务端顺序重建
- 验证：8 门禁全链路模拟（同步/收藏/拖动/删项/number id）+ 坏数据自愈用例，全部通过；tsc 零错误

## ForEach.count 已废弃（同日第四轮）

运行时 ERROR：`ForEach.count is deprecated, use ForEach.data instead`。

- 门禁列表改用 `data: Observable<T[]>` + `builder` + `editActions="move"`，两段（收藏/其他）各一个 Observable
- data 模式没有 onMove：系统拖拽直接改 Observable 数组 → `subscribe` 回写 `ql_door_prefs`（写前比对 Storage 防自写循环）
- 外部变化用签名字符串比对，变了才 setValue 重建
- 兜底：`DoorListTab` 渲染时把当前顺序写进模块级 `liveOrder`，退后台/点刷新小组件时 `flushLiveOrder()` 落盘
- 注意：Scripting 的 `useEffect(setup, deps)` 的 deps 是**必填**，不能省（少了就 TS2554）

## 小组件数据对不上（同日第五轮）—— 加了可验证诊断

现象：App 显示 A座大堂/B座大堂/B座一楼后门，小组件显示 B座负一楼电梯/B座大堂/B座负一楼电梯（新），刷新无变化。
结论方向：两边数据完全不同，不可能是排序算错（同一份 ql_doors+prefs 经同一函数），只能是某一侧根本不是这份数据 ——
可能是小组件绑到了另一个脚本、或桌面快照从未重跑、或 Storage 不共享。本地无法复现，所以不再猜，改为装诊断。

- `BUILD_TAG`（protocol.ts）：每次改小组件相关代码就动它
- `ql_widget_diag`：widget.tsx 在 present 之前写入 {ts,count,ids,names,orderLen,faveLen,version}
- App「我的 → 数据快照」同屏对比 App 读到的 / 小组件渲染的，附判读表（README 附十九）
- 真修：App 回前台重读 ql_doors（小组件里的同步会写这个 key）；刷新改成 reloadAll+reloadUserWidgets+reloadTestWidgets 全打

下一步（若诊断显示 Storage 不共享）：改走 FileManager.appGroupDocumentsDirectory 的 JSON 文件通道。
