# 发布私钥备份、恢复与轮换

每个已发布脚本包都有独立的发布私钥，用于签署该脚本包的新版本。它与 GitHub 登录、许可证 API 令牌、激活码和接收者设备密钥分别独立。Scripting 将它保存在发布设备的私有存储中，不会上传到 API。

在可编辑项目中打开**发布加密脚本 → 发布私钥**。当前账号需要已启用 Scripting 开发者身份。

## 保存加密备份

1. 首次发布项目，创建脚本包和发布私钥。
2. 打开**发布私钥 → 导出加密私钥备份**。
3. 输入高强度备份密码并确认。密码为 12–1024 个 UTF-8 字节，空格和大小写均有意义。
4. 选择**保存加密备份**，将 `.scriptingkey` 文件保存到自己控制的位置。
5. 将密码另存，优先使用密码管理器；再将一份加密备份保存到断开连接的存储介质。

导出文件经过加密，不包含 GitHub 登录信息、API 令牌、激活码或脚本源码。密码保留在设备上。关闭页面或 App 进入后台时会清空密码输入框。

备份对应一个脚本包和开发者账号，不能用一个脚本的备份替换另一个脚本包的私钥。文件中的脚本包和公钥编号可见，私钥内容经过加密。

## 在其他设备或项目中恢复

1. 登录同一个 GitHub 账号，并启用其 Scripting 开发者身份。
2. 打开需要继续发布原脚本包的可编辑项目。
3. 发布之前，打开**发布私钥 → 恢复私钥备份**。
4. 选择备份文件，输入密码，再选择**恢复发布私钥**。
5. Scripting 向服务端核对账号、脚本包和当前发布公钥。恢复后，下次发布会延续原来的脚本包。

恢复不会替换可编辑源码。如果所选项目已经关联另一个已发布脚本包，恢复会被拒绝，请使用尚未关联脚本包的可编辑项目。首版按本地项目名称关联发布状态：发布项目改名前，请先导出备份；改名后再次发布之前，先在新名称下恢复备份。

已轮换退役的旧私钥备份会被拒绝，请使用最近一次轮换之后导出的备份。仅凭 GitHub 登录无法重新生成丢失的私钥。如果可用私钥和当前备份均已丢失，就无法继续为原脚本包签署新版本；发布新脚本包属于另一项操作，不会自动转移原来的许可证。

## 轮换发布私钥

选择**轮换发布私钥**并确认。你需要持有原私钥，并以脚本包所有者身份在线登录。Scripting 创建新私钥，并使用原钥授权和新钥持有证明，请求服务端切换到新公钥。

成功后请立即导出新的加密备份，原备份将无法继续发布新版本。已有脚本版本仍然有效，原激活记录保持不变，用户仍可离线运行已激活版本。轮换不会撤销这些离线授权。

如果响应丢失，页面会显示**续办密钥轮换**。请续办已经保存的操作，不要覆盖恢复或重新发起一次轮换。Scripting 会在私有存储中保留待确认的密钥，直到能确认结果。如果另一台设备抢先完成了另一项轮换，请先恢复该设备的当前备份，再继续发布。

当前格式每个脚本包最多支持 32 次轮换，并保留完整授权历史；达到上限会拒绝继续轮换，不会丢弃旧证明。即使原设备仍然可用，也应保留最新备份。

## 接收者更新

轮换后发布的脚本包会携带原钥授权新钥的证明。Scripting 在已有受保护脚本包上安装更新之前，会核对这种连续关系；不同公钥缺少证明时会被拒绝。

接收者需要使用支持受保护脚本和发布钥轮换的 Scripting 版本。普通可编辑脚本继续沿用原来的导入和运行方式。

## API 凭证

外部许可证 API 令牌不能导出、恢复或轮换发布私钥。轮换后，它们仍可管理同一个脚本包的许可证。App 账号会话负责公钥登记和轮换请求；管理令牌请求中不应包含私钥或备份密码。
